## 附录：决策记录（ADR）

### ADR-001 为什么用 Python 3.11 而不是继续用 3.9

- 背景：本机 Anaconda base 为 3.9.13。
- 事实：`fastapi 0.162.0`、`langchain-deepseek 1.1.1`、`langgraph 1.2.19` 均要求 Python ≥ 3.10。
- 决策：新建 conda 环境，Python 3.11。
- 后果：需要重新安装依赖；与 base 环境隔离，避免污染。
- 备选：锁旧版本（FastAPI 0.115 + LangChain 0.3），但会失去新特性且维护成本高，不采用。

### ADR-002 为什么排盘不让 LLM 直接做

- 背景：LLM 直接排盘会出现星曜错位、四化错误，且不可复现。
- 决策：排盘与规则全部确定性计算，LLM 只做解释与组织语言。
- 后果：需要维护规则库与黄金盘测试；但换来可测试、可解释、可缓存。
- 备选：LLM 直接生成命盘 JSON，不采用。

### ADR-003 为什么 RAG 要混合检索

- 背景：古籍术语（如“廉贞七杀”“火贪格”）是低频专有词，纯向量检索容易召回语义相近但术语不符的片段。
- 决策：dense + BM25 双路召回，RRF 融合，再 rerank。
- 后果：索引与评测复杂度上升；但检索质量与可解释性更好。
- 备选：纯向量检索，作为降级方案保留。

### ADR-004 为什么默认三合 + 中州

- 背景：两套体系在四化重点、空宫处理、断语风格上差异明显。
- 决策：默认 `sanhe_zhongzhou`，倪海厦模式作为可切换配置。
- 后果：首版规则与语料聚焦，评测基线清晰；二期再扩展。
- 备选：双体系同时首发，范围过大，不采用。

### ADR-005 为什么用 SQLite 而不是 PostgreSQL

- 背景：确定本机运行、无部署、Docker 未安装。
- 决策：SQLite + SQLAlchemy 2.0 + Alembic，开启 WAL。
- 后果：零配置、单文件备份；单机低并发足够。表结构避免 SQLite 方言，未来可迁 PostgreSQL。
- 备选：PostgreSQL（需安装服务），本期不采用。

### ADR-006 为什么手相要接 Qwen-VL

- 背景：DeepSeek API 只支持文本，不能读图。
- 决策：手相照片先由 Qwen-VL（DashScope）抽取结构化掌纹特征，用户确认/修正后，再由 DeepSeek 结合命盘做互证。
- 后果：多一个 API Key 与图片外发告知；但手相能力完整，且视觉与推理解耦。
- 备选：纯手动填写掌纹特征（无额外 API，但体验差），作为降级方案保留。

### ADR-007 为什么 Embedding 先用 API

- 背景：本地 BGE-M3 需 PyTorch、2GB+ 模型与较长下载；本机无 GPU，CPU 推理慢。
- 决策：默认硅基流动 `BAAI/bge-m3` API，本地 `bge-small-zh-v1.5` 兜底。
- 后果：启动快、成本低；依赖网络与第二家 API Key。
- 备选：纯本地 BGE-M3，适合离线场景，本期不作为默认。
